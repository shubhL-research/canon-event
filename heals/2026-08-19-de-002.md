Follows `2026-08-19-de-001.md`, which was refused. That refusal named exactly
three defects; this heal was written against those three and nothing else.

## What was asked for

Three narrow instructions, each naming the observed wrong value rather than
describing the desired behaviour in the abstract:

1. `ean` returns the review star rating, "4.1 ud af 5 stjerner". It must read the
   barcode digits from the product information table, **and be empty if that
   table has no EAN row**.
2. `brand` returns the visit-the-store link text. It must return the manufacturer
   name with that wording removed.
3. Add `page_language`, read from the `html` element's `lang` attribute.

The third is not a repair. It is instrumentation added because DE-001 revealed
that the arm could not prove which market answered it.

`ean: null` is the correct answer, not a failure. The instruction was explicit
that an absent EAN row must produce an empty field, and this product page has no
EAN row. A template that invented digits here would be worse than one that
returns nothing, because the digits would be matched against.

## The one that mattered

`page_language: "de"`.

DE-001's preview came back in Danish from the same domain, quoting EUR, and
nothing in the row could have told us. The arm was capable of returning a
non-German page that passed every check we had. That is not a cosmetic problem:
the project's central measure compares three countries, and an arm that cannot
prove its own country makes that comparison meaningless.

The field is now read from the page's own `lang` attribute, which the storefront
writes in response to the session that reached it. It is inside the fetched
document rather than in our configuration, which is the property that makes it
evidence rather than an assertion.

`collect/normalise.py` carries the corresponding rule: **page language is the
geo attestation, currency is corroboration.** The order was the other way round
before DE-001.
