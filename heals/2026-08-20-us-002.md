## What was asked for

The largest open gap in the geo argument, named in the README: the exit
attestation in `data/attest/` went through the CLI's default unlocker zone, not
through a collector session. It proves geo targeting resolves. It says nothing
about the exit the collectors themselves use, and nothing can until a collector
issues an attestation request **in the same stage as its product fetch**.

So the heal asked for exactly that:

> Before extracting products, issue one additional request to
> https://brdtest.com/myip.json in the same stage as the product fetch, parse its
> JSON response, and add three fields to every emitted row: exit_ip, exit_country,
> asn_org. If that request fails, leave all three fields absent rather than
> guessing. Keep every existing field exactly as it is.

26 steps. Stopped at the approval gate with a proposed two-step template.

## Why the preview could not decide it

`preview_result` was empty. On the earlier US refusal that was the whole case, but
here it proved nothing: the preview ran against
`amazon.com/s?k=Remington+D3190DCDN`, and the **production** template returns zero
rows for that same URL. An empty preview was the query, not the repair.

Refusing on that basis would have been wrong in the same way approving on a green
status would have been. So the draft was run instead.

## What the draft actually did

`bdata scraper run <id> --version=dev` against a query known to return rows — one
taken from the archive, where it had produced 798 listings on the production
template.

    draft     240 rows, every one containing exactly two fields:
              input, product_page_url

    exit_ip        ABSENT
    exit_country   ABSENT
    asn_org        ABSENT
    title          absent
    add_to_cart_button  absent
    brand, barcode, availability, currency, seller, page_language  all absent

The heal did not add the attestation. It removed the extraction.

Production, re-run after the refusal, returns 240 rows carrying
`add_to_cart_button, availability, barcode, brand, currency_symbol` and the rest.
Nothing was lost.

## Why this one matters more than the refusal

This is the second time a heal on this collector has answered by emitting
URL-only rows, and the second time it would have been promoted by any check that
reads a status field. `awaiting_approval` was returned both times.

What is different is how it was caught. US-001 was refused by reading preview rows.
Here the preview was uninformative, and the thing that decided it was
`version=dev` — running the proposed template against real input before promoting
it. That is the documented path and it should have been the first move both times.

## The gap stays open, and stays named

The collectors still do not attest their own exit. `data/attest/` still proves
only that geo targeting resolves through the unlocker zone, and the ASNs there
still belong to hosting companies rather than carriers, which is why the wording
is geo-accurate rather than residential.

Two ways forward, neither taken today:

- A sharper heal prompt that names the fields to preserve explicitly rather than
  saying "keep every existing field", since twice now that instruction has been
  the thing discarded.
- Building the collector in the Scraper Studio IDE rather than through the AI
  Agent, where the request can be written directly instead of described.

Until one of those lands, the wall reads `exit not attested on this sweep` on
every arm, which is true.
