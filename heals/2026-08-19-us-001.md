The second refusal, and a different failure mode from `2026-08-19-de-001.md`.
That one returned wrong values. This one returns no values.

## The break, as observed

Not staged. The collector was built cleanly and failed on its first real input:

    error_code   wait_element_timeout
    message      waiting for selector "div[data-component-type=\"s-search-result\"]"
                 failed: timeout 30000ms exceeded
    input        https://www.amazon.com/s?k=737052268675

The search-results container never appeared within thirty seconds. The needle is
`737052268675`, a real EAN from Safety Gate notice A12/02381/24.

Worth noting for the write-up: this is the third distinct Amazon fault in one
day, across two Amazon properties, against zero faults on the regional
marketplace. Bright Data's own documentation says the AI Agent shines on
regional ecommerce and that the large marketplaces are covered by pre-built
library scrapers — which the competition rules disqualify. The pattern in this
ledger is consistent with that.

## What was asked for

> Every search page fails with wait_element_timeout waiting for the selector
> div[data-component-type="s-search-result"]. The search results grid did not
> appear within 30 seconds. Wait for whichever results container amazon.com
> actually renders, handle the case where the page returns a robot check or an
> empty result set by reporting that instead of timing out, and then extract the
> product rows as before.

Six steps. The DE heal that eventually succeeded took twenty-one.

## What the canary found

The proposed template no longer times out. It returns two rows:

```json
[ { "url": "https://www.amazon.com/dp/B0DX1DV8VK" },
  { "url": "https://www.amazon.com/dp/B001F0IDPS" } ]
```

That is the entire row. No title, no brand, no price, no currency, no
availability, no buy control, no part number, no barcode, no page language.

**Every field the RED gate needs is gone.** A row like this cannot re-assert an
identifier, cannot show a buy control, and cannot prove which market answered.
It would be adjudicated `DISCARDED` on every input, forever, while the job
reported success and the arm reported rows.

`contract/states.json` states the principle this refusal rests on:

> A repair that makes everything match is as broken as one that matches nothing.

This is the literal second case. The heal satisfied the instruction it was given
— stop timing out — by discarding the extraction that made the collector worth
running. The instruction was too narrow, and that is a fault in the prompt as
much as in the repair.

## Why refusing was correct, and why it is cheap

An approved template returning URL-only rows is worse than a broken one. A broken
collector is loud: the arm is withheld and the wall goes black. A collector that
returns well-formed rows containing nothing is quiet — the sweep succeeds, the
rows validate, the discard counter climbs, and the arm looks like it is working
while measuring nothing at all.

That is precisely the failure this project exists to refuse, arriving from
inside our own tooling rather than from the marketplace.

The CLI's own note on rejection is the reason the gate is worth having:

    the heal did not complete, but scraper c_mt01usw31e8y5ubqjs is unchanged
    and still works as it did before

Refusing costs one heal. Approving costs the arm.
